## 3. Concepts Studied

### Intercepting proxy

An intercepting proxy sits between a browser and a web application. It allows HTTP requests and responses to be inspected and, in an authorised environment, deliberately modified.

Burp Suite was used to understand how browser requests are transmitted to the server and how responses are returned.

### Proxy HTTP history

Proxy HTTP history provides a record of captured requests and responses.

It helps identify:

- HTTP methods and request paths.
- Host information.
- Query parameters.
- Request headers.
- Cookies.
- Response status codes.
- Server response content.

### Repeater

Repeater allows a captured request to be sent again and compared with controlled variations.

It is useful for testing a hypothesis because one variable can be changed while the remaining request details are kept consistent.

### Target scope

Target scope limits the investigation to the authorised training application.

Restricting scope helps prevent unrelated browsing traffic from becoming part of the investigation.

## 4. Practical Investigation

### Selected application feature

The selected feature was the product-category filtering function in the PortSwigger training lab.

The application displayed product categories such as:

- All
- Accessories
- Food & Drink
- Lifestyle
- Pets

I selected the Accessories category to observe the HTTP request generated by the browser.

### Captured HTTP request

The captured request was:

```http
GET /filter?category=Accessories HTTP/2
```

The request contained the following relevant information:

| Field | Observation |
|---|---|
| Method | GET |
| Request path | `/filter` |
| Query parameter | `category` |
| Parameter value | `Accessories` |
| Protocol | HTTP/2 |
| Host | PortSwigger lab host |
| Cookie | Session cookie present; value excluded |
| Request body | No body observed |

### Expected normal behaviour

When a user selects a category, the application should display products associated with that category.

The category value is supplied through the URL query string.

The application should treat this value as data and should not allow it to change the intended database query structure.

## 5. Baseline and Controlled Comparison

The original request used the following value:

```text
category=Accessories
```

This established the baseline category selection.

For a one-variable comparison, the intended change was:

```text
category=Pets
```

Only the category value should change. The HTTP method, host, and other request details should remain consistent.

A different product list is expected when a different category is selected. Such a difference alone does not demonstrate a vulnerability.

**Evidence limitation:** The captured request and browser screenshot establish the original Accessories request and visible page behaviour. Exact Repeater status codes, response lengths, and comparison results should only be recorded from the actual Repeater response.

## 6. Security Concepts Learned

### URL parameters and encoding

URL parameters communicate values from the browser to the server.

URL encoding represents characters in a URL-safe format, but it does not validate input or prevent SQL injection.

### Cookies and sessions

Cookies may be sent by the browser to maintain application session state.

A cookie sent in a request is different from a cookie set by the server through a `Set-Cookie` response header.

Session cookie values must be treated as sensitive information and excluded from published screenshots and documentation.

### Redirects and response codes

HTTP responses can include status codes and redirects.

A status code or response-length difference must be interpreted in context. It does not independently establish a security vulnerability.

### Client-side and server-side controls

Client-side checks can improve usability, but they cannot replace server-side security enforcement.

The server must independently validate input and enforce access permissions.

## 7. Hypothesis-Driven Analysis

A reliable investigation begins with a hypothesis about expected application behaviour.

For this lab, the relevant security question is whether the category parameter is handled safely when the application constructs its database query.

The existence of a category parameter does not prove SQL injection.

Additional controlled lab evidence is needed to establish whether user-controlled input can affect SQL query structure or retrieve information that should remain hidden.

## 8. Secure Engineering and Mitigation

### Primary mitigation

Use parameterised database queries or prepared statements.

These separate SQL query structure from supplied data values and prevent ordinary user input from being interpreted as executable SQL syntax.

### Defence in depth

- Validate input against expected types and allowed values.
- Apply least-privilege database permissions.
- Avoid exposing detailed database error messages.
- Keep application dependencies and database libraries maintained.
- Log errors securely for investigation.

### Regression testing

Developers should verify that:

1. Valid category values return the expected products.
2. Unexpected input is handled safely.
3. User-controlled values cannot change the intended SQL query structure.
4. Unauthorised database information is not exposed.
5. Existing filtering functionality continues to work after remediation.

## 9. Investigation Limitations

- The investigation was restricted to an authorised PortSwigger training lab.
- The captured request demonstrates the category parameter but does not independently prove SQL injection.
- The exact Repeater response measurements must be supported by saved response evidence.
- A changed response does not automatically indicate a security flaw.
- No real production system or unrelated website was tested.
- The complete server-side database implementation was not established from the browser request alone.

## 11. Reflection

This week helped me understand that Burp Suite is an investigation tool rather than an automatic vulnerability detector.

By examining a normal product-category filtering request, I learned how a browser communicates with a web application through HTTP and how query parameters are included in a request.

I also learned the importance of establishing a baseline before modifying a request. Changing only one parameter makes it easier to understand which differences are associated with the change.

An important lesson was that observing a parameter or receiving a different HTTP response is not sufficient evidence of a vulnerability. Security conclusions must be based on reproducible observations, appropriate context, and consideration of alternative explanations.
